# What the build writes, and what each file is for

You write one kind of file: the `.s0ma` file. Everything a s0ma project runs on is written from those files by `s0ma build`, and written again every time you build. This page opens the build directory and goes through what is in it: what each file is, who reads it, and why none of them is yours to edit.

It uses the smallest module there is, the one on the [survival card](../../packages/s0ma-dsl/docs/survival_card.md), saved as `src/greeter.s0ma` in a project whose `[tool.s0ma]` table says `source_roots = ["src"]`:

```s0ma
module greeter
    layer: DOMAIN
    version: 0.1.0
    intent: "Builds greeting documents for people."
    exports: [greet]
    requires: [json]
    uses: none
    soft_requires: none
    runtime_only_requires: none
    deferred_requires: none
    exports_helpers: none

nerve greet :: DOMAIN
    kind: FUNCTION
    visibility: PUBLIC
    intent: "Return a JSON greeting for a name."
    expects: "name is a non-empty string"
    guarantees: "returns a non-empty JSON string"
    forbids: none
    evaluates_at: FUNCTION_BOUNDARY
    provides: none
    returns: none
    raises: none
    interface: none
    latency_ms: none
    depends_on: none
    internal: none
    expected_exceptions: none
    consumes_via_dict: none
    declares_attributes: none
    covered_by: none
    ---
    def greet(name):
        return json.dumps({"hello": name})
```

## 1. What one build leaves behind

After `s0ma build`, the build directory holds the files below. The directory is the one `build_dir` names in the `[tool.s0ma]` table; a project made with `s0ma new project` calls it `build`.

```text
build/
├── greeter.py            the module as Python: what actually runs
├── greeter.s0ma.json     the canonical IR: the module described as data, for tools
├── greeter.s0ma.map      the source map: which lines of greeter.py came from which lines you wrote
├── build.s0ma.json       the manifest: every module the build wrote, and the order to load them in
├── build.s0ma.pyi        a type stub: the built modules, described for a type checker
├── __init__.py           marks the directory as a Python package
├── self_context.json     the system described for an AI model working inside your application
├── self_prompt_card.md   the same description, as a short card
└── .s0ma.cache/          what this build did, so the next one can skip unchanged modules
```

The first three are written for every module, and named after it. The rest are written once for the whole build. A project that declares documents with `doc-ref` or `doc-guide` also finds them rendered here, each at the `output:` path it names.

## 2. How one file becomes several

The build does three things, in this order.

1. **It reads.** Each file is split into its header and its declarations, the value on every line is read, and the code under each `---` is lifted out exactly as it was written.
2. **It checks.** Each file is checked on its own: every line a declaration must write is there, the names are real, and the kinds and layers are ones the language allows. The files are then checked against one another: every `uses:` entry must name something another file exports, and no two files may depend on each other in a circle. If the check finds an error, the build stops there and writes nothing.
3. **It writes.** From its checked reading of each file, the build writes the Python, stamps it with two fingerprints and a pointer back to the source, makes sure Python can read the result, and then writes the canonical IR and the source map beside it. When every module is written, it writes the files that describe the build as a whole.

The Python and the canonical IR are written from the same checked reading of your file, so they cannot disagree about what it declares. The build is also deterministic: built twice by the same version of s0ma, the same source gives the same files, byte for byte.

## 3. `greeter.py` — the module Python runs

```python
"""greeter — Builds greeting documents for people.

Auto-generated by s0ma DSL transpiler v1.0.0.
Do not edit manually — edit the .s0ma source instead.
"""
# s0ma-source-hash: sha256:fd621426906456c7
# s0ma-output-hash: sha256:f0753e4c6575511f
# s0ma: generated from src/greeter.s0ma — edit the .s0ma source, never this file.

import json

from s0ma.decorators import component
from s0ma.models import Contract
from s0ma.types import ComponentKind, Layer
from s0ma_dsl.runtime_bridge.registration import register_module

__all__ = ["greet"]

register_module(
    name="greeter",
    layer=Layer.DOMAIN,
    version="0.1.0",
    intent="Builds greeting documents for people.",
    exports=["greet"],
)

@component(
    name="greet",
    kind=ComponentKind.FUNCTION,
    layer=Layer.DOMAIN,
    intent="Return a JSON greeting for a name.",
    contracts=Contract(
        preconditions=["name is a non-empty string"],
        postconditions=["returns a non-empty JSON string"],
    ),
    metadata={"visibility": "PUBLIC", "evaluates_at": "FUNCTION_BOUNDARY"},
)
# s0ma: src/greeter.s0ma:33 (nerve greet)
def greet(name):
    return json.dumps({"hello": name})
```

Read from the top:

- The docstring names the module and gives its `intent:`.
- `# s0ma-source-hash:` is a fingerprint of the `.s0ma` text this file was built from, and `# s0ma-output-hash:` is a fingerprint of this file as the build wrote it. Change one character and the fingerprint no longer matches.
- `# s0ma: generated from src/greeter.s0ma` names the file to edit instead of this one.
- `import json` is there because the header says `requires: [json]`. Imports are declared in the header and written by the build, never typed into a body. The four imports after it are s0ma's own.
- `__all__` lists the module's `exports:`.
- `register_module(...)` is the module header, recorded with s0ma when Python loads the file.
- `@component(...)` is the nerve's description, carried by the function it describes: its name, kind, layer and intent, and its `expects:` and `guarantees:` as a contract, what must be true before it is called and what it promises afterwards.
- The `# s0ma:` comment above the function names the source file and the declaration the code below came from.
- Last comes your code, as you wrote it.

**Who reads it: Python.** Importing the module runs `register_module` and every `@component`, and each one records its part in s0ma's runtime registry. That record is the self-model, the running system's own account of what it is made of, and it is what s0ma's verifiers and introspection read. It is also why the file imports s0ma: a project that runs its built code needs `s0ma-core` and `s0ma-dsl` among its dependencies, and the build warns with `HOST_RUNTIME_UNDECLARED` when they are missing.

## 4. `greeter.s0ma.json` — the canonical IR

IR stands for intermediate representation: the module described as data rather than as code. Here is part of it:

```json
"components": [
  {
    "canonical_id": "greeter::greet",
    "declaration_type": "nerve",
    "fields": {
      "covered_by": {"state": "none"},
      "evaluates_at": "FUNCTION_BOUNDARY",
      "expects": {"state": "value", "value": "name is a non-empty string"},
      "forbids": {"state": "none"},
      "guarantees": {"state": "value", "value": "returns a non-empty JSON string"},
      "raises": {"state": "none"}
    },
    "intent": {"state": "value", "value": "Return a JSON greeting for a name."},
    "kind": "FUNCTION",
    "visibility": "PUBLIC"
  }
],
"imports": {
  "requires": {"state": "value", "value": ["json"]},
  "uses": {"state": "none"}
},
"schema_version": "3.0.0"
```

- `schema_version` names the format, so a program reading the file can refuse a version it does not understand.
- Each declaration is one entry under `components`, named `greeter::greet`, module and part, with its kind, visibility and intent.
- Every line you wrote is there under `fields` (a few are shown above), and each carries its state: `{"state": "value", ...}` for an answer, `{"state": "none"}` for "there is nothing here", and `{"state": "pending", "reason": ...}` for "not decided yet". An unanswered question and an answer of nothing never look the same.
- Beside the components, `imports` and `exports` repeat the header, and `edges` hold the connections between parts: the ones you wrote down (`authored`), the ones the build worked out for itself (`derived`), and which tests cover which parts (`verification`).

**Who reads it: anything that needs to know what the module contains without reading code.** `s0ma inspect`, and the `inspect_module` tool of the MCP server, answer from it. `s0ma graph` and studi0's picture of the system are drawn from it, and the two self-context files in section 6 are built from it. That is the point of the canonical IR: an agent or a tool never has to parse a `.s0ma` file, or guess from the Python, to learn what a module declares.

## 5. `greeter.s0ma.map` — the way back to your source

The source map records which lines of `greeter.py` came from which lines of `greeter.s0ma`. For the module header it reads:

```json
"module_header": {
  "output_all": {"end_line": 17, "start_line": 17},
  "output_header": {"end_line": 5, "start_line": 1},
  "output_imports": {"end_line": 15, "start_line": 6},
  "output_registration": {"end_line": 25, "start_line": 19},
  "source": {"end_line": 11, "start_line": 1}
}
```

Lines 1 to 11 of your file became the docstring, the imports, `__all__` and the registration of `greeter.py`. Each declaration has an entry of the same kind under `declarations`: the lines it came from, the lines it became, and, within those, where the decorator is and where your code is.

**Who reads it: tools that need to turn a line of the running Python back into the line you wrote,** such as a debugger, an error reporter or an editor. `s0ma-dsl` ships a small reader for it, `resolve_output_line` in `s0ma_dsl.codegen`. A person reading `greeter.py` has the `# s0ma:` comments, which do the same job by eye.

## 6. The files that describe the whole build

**`build.s0ma.json`, the manifest.** It has one entry for each module the build wrote. The entry gives its source, its `.py`, IR and source map, a fingerprint of the source and of the output, and its `role`, which is `source`, or `test` for a module `s0ma test` built from a test root. The manifest also lists `topological_import_order`, the modules in an order in which each comes after everything it depends on.

- `bootstrap_imports` in `s0ma-core` loads a built project's modules in that order, the source modules only unless it is asked for more.
- `s0ma doctor`, the MCP server's `project_status` and studi0 compare each module's recorded source fingerprint with the file as it is now, and tell you whether the module is fresh, stale or not built yet.

The manifest keeps what earlier builds recorded. A module you delete keeps its entry, and its files stay in the build directory, until you run `s0ma build --clean`.

**`build.s0ma.pyi`, the type stub.** It declares every built module and a `BootstrapModules` type, so that a type checker such as mypy or pyright can check code that uses what `bootstrap_imports` returns. Nothing in s0ma reads it; it is there for your tools.

**`__init__.py`** marks the build directory as a Python package, so that built modules can import one another. Its docstring says so, and names the manifest as the record of what the build wrote.

**`self_context.json` and `self_prompt_card.md`, the system described for an AI model inside it.** Both are built from the canonical IR of the modules with the `source` role; the test modules `s0ma test` builds into the same manifest are left out, and the JSON records the roles it was built from in `provenance.roles`. The JSON lists every component with its kind, layer, intent and dependencies. The card is a short summary, kept under 2,600 bytes, for an application that asks a model to reason about itself while it runs. The text you wrote, such as intents, is marked as quoted project data and never as instructions. The build health they report is always `unknown`, because a build does not watch a running system. [Runtime self-prompting](../../packages/s0ma-dsl/docs/self_prompting.md) shows how an application uses them.

**`.s0ma.cache/`, the build's memory.** For each module it keeps a fingerprint of the source, including any file the module embeds with `@file`, and of the version of s0ma that built it, and a copy of what the build wrote. When none of those has changed, the next build reuses that work instead of doing it again, so the first build after you upgrade s0ma writes every module afresh. `s0ma build --no-cache` leaves the cache alone, `s0ma build --clean` empties it before building, and `s0ma test` never uses it.

## 7. Why none of these files is yours to edit

Everything in the build directory is derived from your `.s0ma` files. The change you want belongs in the source, and a change made to a derived file is drift: the written record and the thing it describes have parted. s0ma notices it. `s0ma verify` recomputes each file's fingerprint and compares it with the one the build stamped in, so changing a single character of `greeter.py` gives:

```console
$ s0ma verify build
Verifying 2 transpiled file(s)...
  EDITED   build/greeter.py
           (.py was modified after transpilation)

Verified 1 module(s). 0 bootstrap file(s) recognized. 0 unknown.
Coverage: 1 modeled s0ma module(s), 0 roster-adopted file(s), 0 unknown plain-Python file(s).
1 file(s) edited directly.
For edited files: move the hand edits into the .s0ma source and run `s0ma build`, or discard them with `s0ma build --force`.
```

`s0ma check` reports the same file as `GENERATED_FILE_DRIFT`. A build refuses to write over the edited file, and it refuses whether or not the source changed since the last build: a build never reuses its last result while a file it published differs from what it wrote, so the edit is looked at every time, and it is never lost without somebody deciding it should be. There are two ways on. Move the change into the `.s0ma` file; the regenerated file then says the same thing as the edited one, and the build writes it without complaint. Or `s0ma build --force`, which is the decision to discard the edit. [When s0ma refuses, and how to get back to green](drift-recovery.md) walks through both.
