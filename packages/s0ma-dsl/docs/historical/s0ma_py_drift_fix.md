# s0ma Framework Enhancement: Transpiled `.py` Drift Detection

**Date:** March 30, 2026
**Source project:** fr3d (25-module s0ma-dsl agent)
**Applies to:** s0ma-dsl transpiler and s0ma framework tooling
**Status:** Proposed

---

## 1. Background

### 1.1 The Pipeline

s0ma-dsl's transpiler pipeline produces three artifacts from each `.s0ma` source file:

```
source.s0ma  →  source.py        (importable Python)
                source.s0ma.json  (IR / compile-time self-model)
                source.s0ma.map   (source maps for debugging)
```

The `.s0ma` file is the source of truth. The `.py` file is generated output — it carries the header `"Auto-generated by s0ma DSL transpiler v1.0.0. Do not edit manually — edit the .s0ma source instead."` The entire value proposition of the pipeline depends on this contract holding.

### 1.2 The Problem: Silent `.py` Drift

During fr3d development, 9 of 17 test `.py` files were hand-edited directly without updating their `.s0ma` sources. The edits were substantive (replacing mocked tests with real API calls, adding helpers, changing imports) and committed to version control alongside the stale `.s0ma` files.

This happened across multiple commits over a 5-day period:

| Commit | Date | Description | Files Affected |
|--------|------|-------------|----------------|
| `79fa586` | Mar 16 | "update tests from mock to real" | 8 `.py` test files |
| `52cdad9` | Mar 16 | "test improvements" | 6 `.py` test files |
| `b8c5d87` | Mar 18 | (continued edits) | 2 `.py` test files |
| `8728022` | Mar 20 | (continued edits) | 1 `.py` test file |
| `ed32aa0` | Mar 20 | (continued edits) | 1 `.py` test file |

None of these commits touched any `.s0ma` file. The result:

- **9 `.s0ma` files are stale** — they describe tests that no longer match what runs.
- **9 `.s0ma.json` IR files are inaccurate** — compile-time metadata doesn't match runtime behavior.
- **9 `.s0ma.map` source maps are broken** — line mappings point to the pre-edit `.py` structure.
- **Re-transpilation is destructive** — running `s0ma build` would overwrite all the hand-edited improvements with output from the stale `.s0ma` files.
- **The "Do not edit manually" header** in every affected `.py` file was ignored. It's advisory, not enforced.

### 1.3 Why It Happened

1. **Edit loop friction.** The correct workflow (`edit .s0ma` → `s0ma check` → `s0ma transpile` → `pytest`) is a 4-step cycle. When tests are failing and iteration speed matters, the temptation to edit the `.py` directly is high — the feedback loop drops to 1 step (`edit .py` → `pytest`).

2. **No detection mechanism.** Nothing in the s0ma toolchain detects that a transpiled `.py` has diverged from its `.s0ma` source. The transpiler is a one-way pipeline with no verification step.

3. **No enforcement.** The "Auto-generated" header is a comment. There is no checksum, hash, or structural marker that the toolchain can verify.

### 1.4 Scope of Impact

This is not a fr3d-specific problem. Any project using s0ma-dsl is vulnerable to the same pattern:

- A developer (human or AI) edits a `.py` file for expediency.
- The `.s0ma` source is not updated.
- The project accumulates drift silently.
- A future `s0ma build` destroys the hand-edited improvements.
- Or worse: the project never re-transpiles, and the `.s0ma` files become decorative metadata rather than a source of truth.

The problem scales with project size. fr3d has 25 source modules and 17 test modules. A larger project would have more surface area for drift.

## 2. Proposed Solution A: `s0ma build --check` (Drift Detection Mode)

### 2.1 Summary

Add a `--check` flag to `s0ma build` (and optionally `s0ma transpile`) that compares the transpiler's output against existing `.py` files **without overwriting them**. If any `.py` file differs from what the transpiler would produce, the command reports the drift and exits with a non-zero exit code.

### 2.2 User Interface

```bash
# Check a single file
s0ma transpile src/fr3d/domain/config.s0ma --output-dir src/fr3d_build/ --check

# Check full project
s0ma build src/fr3d/ --output-dir src/fr3d_build/ --mode dev --check

# Check tests
s0ma build tests/ --output-dir tests/ --mode dev --check
```

### 2.3 Behavior

**When `--check` is passed:**

1. The transpiler runs its normal pipeline: parse `.s0ma`, validate, generate `.py` output **in memory** (or to a temporary location).
2. For each output `.py` file, compare the generated content against the existing `.py` file on disk.
3. If the files match: report OK, continue to next file.
4. If the files differ: report the file path and a summary of differences (line count delta, first divergent line, etc.). Do **not** overwrite the file.
5. After processing all files, exit with:
   - Exit code `0` if all files match (no drift).
   - Exit code `1` if any files differ (drift detected).

**When `--check` is NOT passed:**

No change to existing behavior. The transpiler overwrites `.py` files as it does today.

### 2.4 Output Format

```
$ s0ma build tests/ --output-dir tests/ --mode dev --check

Checking 17 modules for drift...
  OK    tests/test_domain/test_models.py
  OK    tests/test_domain/test_exceptions.py
  DRIFT tests/test_infrastructure/test_llm.py
        (120 lines differ; first divergence at line 7)
  DRIFT tests/test_infrastructure/test_shell.py
        (43 lines differ; first divergence at line 31)
  OK    tests/test_domain/test_tools.py
  ...

2 files have drifted from their .s0ma sources.
Run `s0ma build` without --check to overwrite, or update the .s0ma sources.
Exit code: 1
```

### 2.5 Implementation Notes

- The comparison should normalize line endings (CRLF vs LF) to avoid false positives on Windows.
- The comparison should ignore the transpiler version comment in the header (e.g., `Auto-generated by s0ma DSL transpiler v1.0.0`) to avoid flagging drift when only the transpiler version changes.
- Consider supporting `--check --verbose` to show a full diff (similar to `diff -u`) for each drifted file.
- The `--check` flag should also verify `.s0ma.json` and `.s0ma.map` if they exist, not just `.py`.

### 2.6 Use Cases

1. **Developer workflow:** Run `s0ma build --check` before committing to verify no drift exists.
2. **CI pipeline:** Add `s0ma build --check` as a CI step. Fail the build if drift is detected.
3. **Pre-commit hook integration:** A pre-commit hook can call `s0ma build --check` on staged files.
4. **Post-edit verification:** After back-porting `.py` edits into `.s0ma` and re-transpiling, run `--check` to confirm the `.py` now matches.

## 3. Proposed Solution B: Checksum Embedding in Transpiled `.py` Files

### 3.1 Summary

Embed a machine-readable checksum comment in every transpiled `.py` file that encodes the hash of the `.s0ma` source content at transpile time. The `s0ma check` command (or a new `s0ma verify` command) can then compare this checksum against the current `.s0ma` source to detect staleness — even without re-running the full transpiler.

### 3.2 Checksum Format

Add a comment line near the top of every transpiled `.py` file, immediately after the existing "Auto-generated" header:

```python
"""module_name — Module intent string

Auto-generated by s0ma DSL transpiler v1.0.0.
Do not edit manually — edit the .s0ma source instead.
"""
# s0ma-source-hash: sha256:a1b2c3d4e5f6...
# s0ma-output-hash: sha256:f6e5d4c3b2a1...
```

Two hashes:

- **`s0ma-source-hash`**: SHA-256 of the `.s0ma` source file content at transpile time. Detects when the `.s0ma` source has been updated but the `.py` has not been re-transpiled (stale output).
- **`s0ma-output-hash`**: SHA-256 of the transpiled `.py` content (excluding the hash lines themselves). Detects when the `.py` has been hand-edited after transpilation (modified output).

### 3.3 Verification Commands

```bash
# Verify a single file's checksums
s0ma verify tests/test_infrastructure/test_llm.py

# Verify all transpiled files in a directory
s0ma verify tests/

# Integrate with existing check command
s0ma check src/fr3d/domain/config.s0ma --verify-output
```

### 3.4 Verification Logic

For each `.py` file with `s0ma-source-hash` and `s0ma-output-hash` comments:

1. **Source staleness check:** Hash the current `.s0ma` source file. Compare against `s0ma-source-hash`.
   - Match → `.s0ma` hasn't changed since last transpile.
   - Mismatch → `.s0ma` has been updated but `.py` was not re-transpiled. Report: "Stale output — re-transpile needed."

2. **Output tampering check:** Hash the current `.py` content (excluding hash comment lines). Compare against `s0ma-output-hash`.
   - Match → `.py` hasn't been modified since transpilation.
   - Mismatch → `.py` was hand-edited after transpilation. Report: "Modified output — .py was edited directly."

3. **Combined states:**

| Source Hash | Output Hash | Diagnosis |
|-------------|-------------|-----------|
| Match | Match | Clean — no drift |
| Match | Mismatch | `.py` was hand-edited (source unchanged) |
| Mismatch | Match | `.s0ma` was updated, `.py` not re-transpiled |
| Mismatch | Mismatch | Both changed — manual reconciliation needed |

### 3.5 Output Format

```
$ s0ma verify tests/

Verifying 17 transpiled files...
  CLEAN  tests/test_domain/test_models.py
  CLEAN  tests/test_domain/test_exceptions.py
  EDITED tests/test_infrastructure/test_llm.py
         (.py was modified after transpilation — source hash matches, output hash differs)
  STALE  tests/test_infrastructure/test_executor.py
         (.s0ma was updated but .py was not re-transpiled)
  CLEAN  tests/test_domain/test_tools.py
  ...

1 file edited directly, 1 file stale.
Run `s0ma build` to re-transpile from .s0ma sources.
Exit code: 1
```

### 3.6 Implementation Notes

- **Hash algorithm:** SHA-256 is standard and collision-resistant. Truncating to the first 16 hex characters (64 bits) is sufficient for drift detection (this isn't a security application).
- **Hash exclusion:** When computing `s0ma-output-hash`, the hash comment lines themselves must be excluded from the computation to avoid a circular dependency. Use a simple regex strip of lines matching `^# s0ma-(source|output)-hash:`.
- **Backward compatibility:** Files transpiled before this feature will have no hash comments. `s0ma verify` should report these as "UNKNOWN — no checksum (transpile to add)." rather than failing.
- **Re-transpilation updates hashes automatically:** Every `s0ma transpile` / `s0ma build` run recalculates both hashes and writes them into the output `.py`. No additional step needed.
- **`.s0ma.json` and `.s0ma.map`:** Consider embedding the source hash in these files as well (e.g., a `"source_hash"` field in the IR JSON). This would allow IR consumers to detect staleness independently.

### 3.7 Advantages Over Solution A

Solution A (`--check`) requires re-running the transpiler to detect drift. Solution B (checksums) can detect drift with a fast hash comparison — no parsing, no code generation. This makes it suitable for:

- **Editor integrations:** A VS Code / Cursor extension could display a warning icon on `.py` files with mismatched checksums.
- **Git hooks:** A pre-commit hook can verify checksums in milliseconds, even on large projects.
- **Self-model queries:** fr3d (or any s0ma agent) could verify its own transpiled output integrity by checking hashes at runtime.

### 3.8 Limitations

- Checksums detect *that* drift occurred, but not *what* drifted. Solution A's `--check` mode shows actual diffs. The two solutions are complementary.
- If the transpiler itself changes (e.g., different formatting, new imports), `s0ma-output-hash` will report "EDITED" for all files even though the `.py` content is functionally equivalent. This can be mitigated by re-transpiling after transpiler upgrades and verifying tests pass.

## 4. Relationship Between Solutions A and B

The two solutions are complementary and can be implemented independently:

| Aspect | Solution A (`--check`) | Solution B (checksums) |
|--------|----------------------|----------------------|
| Detection speed | Slow (full transpile) | Fast (hash comparison) |
| Diff visibility | Yes (can show diffs) | No (only detects drift) |
| Requires transpiler run | Yes | No |
| Works in editor/IDE | No (CLI only) | Yes (hash is in file) |
| Detects `.s0ma` staleness | Yes (implicitly) | Yes (explicit `s0ma-source-hash`) |
| Detects `.py` tampering | Yes (implicitly) | Yes (explicit `s0ma-output-hash`) |
| Backward compatible | Yes | Yes (no-hash = UNKNOWN) |

**Recommended implementation order:**

1. **Solution B first** — it's lower cost to implement (hash computation + comment injection), provides fast detection, and enables editor integrations.
2. **Solution A second** — it builds on the existing transpiler and provides the detailed diff view that Solution B lacks.

Together, they form a complete drift detection system: Solution B for fast, always-on monitoring; Solution A for detailed investigation when drift is detected.
