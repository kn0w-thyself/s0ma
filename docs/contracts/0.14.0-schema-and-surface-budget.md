**Status:** Frozen for implementation
**Date:** 2026-07-21
**Owner decision:** approved 2026-07-21
**Governing ADR:**
[`ADR-001`](../adr/ADR-001-0.14-gate-integrity-and-value-loop.md)

This document is the compatibility budget for the 0.14 value-loop wave. A
milestone may implement a row assigned to it; it may not add another public
schema, rename a budgeted surface, or change a field below without owner review.

Unknown major versions are refused with a diagnostic that names the supported
major and the migration/rebuild action. Minor additive fields may be ignored only
where that contract already permits them. JSON bytes use UTF-8, LF, deterministic
key ordering, a final newline, POSIX relative paths, and `sha256:<lowercase hex>`.

## 2. Exact score report delta

`s0ma-score@2` keeps the v1 top-level keys and adds `gate_mode`. `mode` remains
the resolved authoring mode. The exact top-level set is:

```text
schema, project, root, mode, gate_mode, overall, faculties, exempt_set,
module_count, public_nerve_count, gate
```

The proprioception metric formerly named `surface_registration` is replaced by:

```json
{
  "registration": {
    "componentized": 0,
    "roster_adopted": 0,
    "unknown": 0,
    "componentized_pct": 0.0,
    "roster_adopted_pct": 0.0,
    "combined_pct": 0.0,
    "detail": "human rendering derived from these counts"
  }
}
```

Only `componentized_pct` contributes to a gate. The `gate` object is:

```json
{
  "mode": "release",
  "floor": 90.0,
  "passes": false,
  "blocked": [
    {"faculty": "metacognition", "metric": "declared_test_evidence", "reason": "nothing_to_measure"}
  ],
  "reasons": ["human rendering derived from blocked and floor"],
  "na_faculties": ["interoception"]
}
```

When `gate_mode` is absent, it is JSON `null`; `gate.mode`, `gate.floor`, and
`gate.passes` are `null`; `gate.reasons` is exactly
`["mode not pinned by caller"]`. A blocked metric makes `passes` false even if
the numeric `overall` clears the floor. Numeric overall may be `null` when the
required population is absent; an absent population never disappears from the
gate calculation.

## 3. Semantic-state syntax and canonical IR

Existing authored syntax remains the `value` form. State-aware fields additionally
accept these whole-value forms:

```s0ma
returns: none
returns: pending("choose the public return contract after API review")
returns: [Result]
```

`pending` requires one non-empty reason string. A bare string containing the word
`none` is content, not state. Canonical IR serializes a state-aware field at its
existing key as one of:

```json
{"state": "value", "value": ["Result"]}
{"state": "none"}
{"state": "pending", "reason": "choose the public return contract after API review"}
```

Omission of a required-state field is a field-specific error. A conditional-state
field is absent only when its applicability predicate is false; when applicable,
it uses the same tagged representation. Presentation fields retain their existing
unwrapped representation and may be absent. Derived fields retain their existing
representation and are rejected if authored.

### Classification legend

- **SR** — semantic-required-state. It must be authored. `V`, `N`, and `P`
  list the allowed `value`, `none`, and `pending(reason)` states.
- **SC** — semantic-conditional-state. The applicability note defines what absence
  means; once applicable it must be authored in an allowed state.
- **PO** — presentation-optional. No state wrapper.
- **D** — derived from source shape, parser, resolver, emitter, or runtime; authors
  cannot set it.
- Structural identity fields use **SR / V**: they are required but cannot be
  `none` or `pending` because compilation cannot proceed without an identity.

## 4. Derived surface contract

An adopted Python module without canonical IR is returned under
`derived_surface`, never `ir`:

```json
{
  "schema": "s0ma-derived-surface@1",
  "authority": "derived",
  "mapped": false,
  "module": "legacy_impl",
  "source": "src/legacy_impl.py",
  "source_hash": "sha256:...",
  "config_hash": "sha256:...",
  "derivation_version": "1",
  "provenance": {"method": "static_python_ast", "imports_executed": false},
  "summary": {"state": "pending", "reason": "machine-derived draft requires author review", "draft": "..."},
  "exports": [],
  "imports": [],
  "confidence": "syntax_only",
  "limitations": ["unverified", "does not satisfy score or gate"]
}
```

Canonical inspection uses `ir` and its document has
`schema_version: "3.0.0"`; it does not also return `derived_surface`.
Derived-cache identity binds the project-relative POSIX `source` path as well
as its content hash, normalized `[tool.s0ma]` hash, derivation/schema versions,
and tool version; a cache hit revalidates every bound field. In
`project_status`, `adopted_files` remains the complete historical ledger, while
roster module rows and `module_registration.roster_adopted` count only current,
existing `.py` files that do not carry both transpiler hash headers.

## 5. Common tool-result contract

Every tool result reaching a tool body uses:

```json
{
  "schema": "s0ma-tool-result@1",
  "ok": false,
  "next_actions": [
    {
      "tool": "check",
      "arguments": {"project_root": "/explicit/root", "gate_mode": "strict"},
      "reason": "Re-run the caller-pinned static gate after the edit"
    }
  ]
}
```

`schema`, `ok`, and `next_actions` are required; tool-specific fields are
additive. `next_actions` may be empty. At build/test time every action tool must
exist in the served snapshot and its arguments must validate against that tool's
input schema. `suggested_next_action` may coexist for one compatibility release
but is rendered from the structured array.

## 6. Host verification and adoption policy

`s0ma-host-verification@1` requires:

```text
schema, ok, gate_mode, interpreter, modules, dependencies, diagnostics,
duration_ms, gate
```

`interpreter` requires resolved path, Python version, implementation, platform,
and installed versions of the three s0ma distributions. Each module record has
name, owner when resolvable, outcome, duration, and bounded stdout/stderr tails.
Dependency records distinguish declared+installed, declared+not-installed, and
runtime-imported+undeclared. Diagnostics use the frozen codes
`DECLARED_DEP_NOT_INSTALLED`, `HOST_RUNTIME_UNDECLARED`, and
`HOST_IMPORT_FAILED`.

At the MCP boundary, `verify_host` follows the common tool-result contract: its
top level is `s0ma-tool-result@1`, and exactly one authoritative
`host_verification` member contains the complete, exact
`s0ma-host-verification@1` document. Host evidence fields are not duplicated at
the MCP top level. The CLI command `s0ma verify-host --format json` remains the
native `s0ma-host-verification@1` document at top level.

`s0ma-adoption-policy@1` is:

```json
{
  "schema": "s0ma-adoption-policy@1",
  "exceptions": [
    {"path_glob": "vendor/acme/**", "category": "vendored", "reason": "upstream-owned source"}
  ]
}
```

Allowed categories are `vendored`, `generated`, `data`, and `bootstrap`.
Canonical policy bytes sort object keys and exception entries by
`(path_glob, category, reason)` before SHA-256. The result reports that hash and
the full matched path inventory.

## 7. Self-context and manifest references

`s0ma-self-context@1` requires:

```json
{
  "schema": "s0ma-self-context@1",
  "generation_version": "1",
  "provenance": {"authority": "canonical_ir", "live_health": false},
  "source_ir": [{"path": "module.s0ma.json", "sha256": "sha256:..."}],
  "components": [
    {
      "id": "module::component",
      "kind": "FUNCTION",
      "layer": "APPLICATION",
      "intent": {"state": "value", "value": "..."},
      "dependencies": []
    }
  ]
}
```

The additive `s0ma-build-manifest@1` member is:

```json
{
  "self_context": {
    "json": {"path": "self_context.json", "sha256": "sha256:..."},
    "prompt_card": {"path": "self_prompt_card.md", "sha256": "sha256:..."}
  }
}
```

Paths are build-root-relative POSIX paths. Older manifests omit the member.
When the member exists, both files and hashes are mandatory. The Markdown card
is a pure rendering of the JSON, includes the fixed trust instruction from
ADR-001, prefixes every authored prose line with `AUTHORED_DATA | `, and carries
no build-time claim of live health.

## 9. Quarantine lifecycle

M0 acceptance modules carry the registered `m0_contract` pytest marker and each
case is `xfail(strict=True)` with its implementing milestone in the reason. The
full baseline therefore remains green. When behavior lands, XPASS is deliberately
red: the milestone must inspect the evidence, remove the XFAIL, and keep the test
as permanent acceptance coverage. Deleting or broadening an assertion to avoid an
XPASS is not an acceptable implementation.

### 10.4 Byte-cost budget

The added surface pays its context cost against the existing NFR-5 budgets,
which are unchanged and still binding:

- Tool descriptions are the authored docstrings: **≤ 4 lines each**, written
  context-economically. The long privacy story lives in `feedback-v1.md`, not in
  a tool description.
- The survival card (`s0ma://guide/survival-card`) keeps its gate-enforced
  **≤ 2 KB** ceiling. A feedback line is added to it **only** if the gate still
  passes with it; otherwise the recognition instruction carries the rule alone
  and the milestone reports the measured byte headroom.
- `self_prompt_card` keeps its existing budget (measured 1780/1800 at M10).
- The server-level recognition instruction is two to three short sentences.
  The FD-13 suggest-offer line is served conditionally per render and is not
  part of the always-served instruction cost.

If any byte budget trips, the milestone STOPS and reports the exact bytes. This
revision covers the contracted count delta only; buying headroom by trimming
another surface, or exceeding a budget, is an owner escalation.

### 11.3 Approved addition — a human-readable title on every tool

Directories that list MCP servers require every tool to carry a title a person can read. Each
tool declaration authors one as `metadata: mcp_tool_title:` in `packages/s0ma-mcp/s0ma_src/tools.s0ma`.

and a malformed title fails the package import, the same way a malformed hint does. The server
serves it in **both** places a client may look, the tool's own `title` and `annotations.title`,
from the one authored value, so the two cannot disagree.

A title is a label, not a description. Changing one later is a client-visible change and takes

### 11.4 Byte cost

Titles touch none of the NFR-5 budgets §10.4 binds: tool descriptions, the survival card,
`self_prompt_card` and the server-level instruction are byte-unchanged. Measured on the
serialized tool list: 20,641 bytes without titles, 21,245 with them — **604 bytes** across
fifteen tools, paid once per `tools/list`.

### 11.5 What this revision does not authorize

No new tool, resource or prompt. In particular the retrofit tools for agents without a shell

## 14. Revision R6 — the forbids line (2026-09-30)

Owner ruling of 2026-09-30, recorded in
[`docs/adr/ADR-014-the-forbids-line.md`](../adr/ADR-014-the-forbids-line.md):
a nerve and a ganglion each carry a `forbids` line, which says what the part
must never do. It must always be written, and it may be `none` or
`pending("reason")`. It goes out in the release that carries this change,
whose number is not named here.

### 14.1 What it adds

One row, added in place to §3's nerve table directly after `guarantees` and to
its ganglion table directly after `on_anomaly`:

| Field | Class / states | Applicability or meaning |
|---|---|---|
| `forbids` | SR / V,N,P | `none` asserts nothing is ruled out |

The line holds one text value, in every shape `expects` accepts. The canonical
IR carries it at `components[].fields.forbids`, in the tagged representation
§3 defines. It is not a sub-field of a `provides:` entry, and on any other
declaration kind it is an unknown field. s0ma checks that the line is there
and what state it is in; it does not read the sentence, and neither verifier
counts it. At runtime it is `Contract.forbids`, written out only when it holds
a sentence.

### 14.2 What it does not change

- **§1.** No versioned document moves. The canonical module IR keeps
  `schema_version: "3.0.0"`: `forbids` is one more state-carrying key on
  records that already carry them.
- **§7.** `s0ma-self-context@1` and the build manifest's `self_context` member
  keep their names, their required members and their rules. The line joins the
  authored states the self-context already carries for a component, and the
  prompt card does not change by a byte.
- **§8.** No tool, resource, prompt, description, schema or annotation changes,
  and the committed surface snapshot does not move.
- **The byte budgets.** No budget in §10.4, or in the revisions after it,
  moves. A served document that shows a sample nerve or ganglion gains the line
  like any other source, inside the ceilings already set.

## 15. Revision R7: the self-context describes the application (2026-10-23)

**Status:** recorded for owner review; not ratified.

Recorded in the form R2 set, by the session that implemented the change, at
the repository gate of 2026-10-23, so the owner can confirm or reverse it.
The evidence is fr3d's build on that day, 103 source modules and 158 test
modules in one manifest. Built from every manifest entry, `self_context.json`
weighed 1,021,910 bytes and listed 1,857 components, 1,416 of them from test
modules; the runtime adapter's `describe` answer, which listed every component
id and every IR record, was 130,808 characters of compact JSON. Built from the
source entries, the companion weighs 381,824 bytes and lists 441 components;
the old `describe` shape would still have cost 28,752 characters on it, and
the new one answers in 2,264.

### 15.1 What it adds

- **`provenance.roles`**, additive under `s0ma-self-context@1`: the manifest
  roles the companion was derived from, `["source"]` by default. The generator
  (`s0ma_dsl.codegen.self_context`) selects manifest entries by role, matching
  `s0ma.bootstrap.bootstrap_imports`, and a caller may pass
  `roles=("source", "test")` to describe both. Older companions omit the field
  and the runtime accepts them; a present value must be a non-empty list of
  role names, or the runtime refuses the companion with its rebuild
  remediation. `generation_version` stays `"1"`.
- **The runtime adapter's answers.** These are the host's tool, not a
  surface the server serves, and no budget here names them; they are recorded
  for completeness. `describe` now carries counts (`component_count`,
  `module_count`, `source_ir_count`, `component_count_by_layer`,
  `component_count_by_kind`), the module names by layer, the roles,
  `build_health`, and the live-health overlay as counts when a registry was
  supplied. `components_by_layer`, which listed every id, and the `source_ir`
  list are no longer keys of `describe`; a host that read either asks
  `components <layer or module>` or `source_ir`, the two commands added for
  that; `component <name>` and `dependencies <name>` are unchanged, and
  `component <name>` gains an `observed` flag beside the record when a
  registry was supplied. The tool definition names all five commands. The
  adapter holds `describe` under 8,000 characters of compact JSON by trading
  module names for per-layer module counts past that line; a test in
  `packages/s0ma-core` holds it there on 3,000 synthetic components over 200
  modules, with and without a registry, and a test in `packages/s0ma-mcp`
  holds it on that package's own build.
- **The card's header line** names the tool and its five commands. It is 1
  byte longer than the line it replaces; the three committed cards remain
  complete, each with an authored-intent sample, and the s0ma-mcp card stands
  at 2,592 of 2,600 bytes.

### 15.2 What it does not change

- **§1.** No versioned document moves.
- **§7.** `s0ma-self-context@1` keeps its required members and their rules;
  the card keeps its trust instruction, its `AUTHORED_DATA |` prefixing, its
  2,600-byte, 240-word budget, and carries no build-time claim of live
  health.
- **§8.** No tool, resource, prompt, description, schema or annotation
  changes, and the committed surface snapshot does not move.
- **The byte budgets.** No budget in §10.4, or in the revisions after it,
  moves.

### 15.3 What this revision does not authorize

- A command-line or `[tool.s0ma]` switch selecting the roles a build's
  companions describe. That is a new public surface; the generator's `roles`
  argument is the only route today.
- A rendering or size-estimating helper in `s0ma.runtime`. The two one-liners
  are written in the self-prompting guide instead; a public helper is a
  decision for the owner.
